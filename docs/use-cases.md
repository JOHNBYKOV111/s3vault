# Use Cases — s3vault

Три сценария, для которых s3vault (S3-совместимый шлюз с дедупликацией, шифрованием и наблюдаемостью) даёт реальную ценность.

---

## 1. Внутренний бэкап с дедупликацией

**Контекст:** команда бэкапит ежедневные снапшоты БД и файлы приложений. 80% данных между снапшотами не меняется.

**Как используется s3vault:**
- Бэкап-агент (restic, borg, custom) пишет объекты через S3 API (`PutObject`).
- s3vault считает SHA-256 каждого объекта, сохраняет **один blob** на уникальное содержимое и создаёт `blob_refs` для каждого объекта.
- Повторные снапшоты с неизменными файлами **не занимают место** — только ссылки.

**Что даёт:**
- **Экономия диска** на 60–80% (зависит от доли неизменных данных). Для 1 ТБ бэкапов с 70% дедупа — **700 ГБ свободно**.
- **Шифрование на диске**: envelope encryption (DEK/KEK), диск украден — данные нечитаемы.
- **Метрика `s3_dedup_ratio`** в Grafana показывает реальную экономию в реальном времени.

**Что проверяется тестами:**
- `TestDedupStore` (два одинаковых объекта → один blob, счётчик ссылок = 2).
- `TestEnvelopeEncryption` (encrypt → decrypt, подмена байта → ошибка).

## 2. Хранилище медиа с Range-запросами и multipart

**Контекст:** сервис отдаёт видео/аудио. Клиенты запрашивают **части файла** (Range) и **докачивают** большие файлы кусками (multipart).

**Как используется s3vault:**
- Загрузка больших файлов — через **multipart upload** (`CreateMultipartUpload` → `UploadPart` → `CompleteMultipartUpload`). Каждая часть стримится на диск, не держится в памяти.
- Отдача — через **Range-запросы** (`Range: bytes=0-1023` → `206 Partial Content` с `Content-Range`). Плеер может начать воспроизведение, не дожидаясь полной загрузки.
- Дедупликация: одинаковые превью/обложки хранятся **один раз**.

**Что даёт:**
- **Стриминг без OOM**: 100 МБ файл загружается через `io.Pipe`, RSS не растёт (проверено `TestChunker_Memory`).
- **Range** — стандартный S3-совместимый протокол, работает с `aws-cli`, `boto3`, `rclone`, плеерами.
- **Multipart** — большие файлы (гигабайты) загружаются кусками, устойчиво к обрывам.

**Что проверяется тестами:**
- `TestMultipartUpload`, `TestMultipartAbort`, `TestUploadPartNonExistentUpload`.
- `TestParseRange` (валидный → 206, невалидный → 416).
- `TestChunker_Memory` (100 МБ через `io.Pipe`, RSS не растёт).

## 3. Мультитенантное хранилище для SaaS

**Контекст:** SaaS-платформа хранит файлы **разных клиентов** (tenant'ов). Нужна **жёсткая изоляция**: клиент A не должен видеть данные клиента B, даже если знает ключ.

**Как используется s3vault:**
- Каждый запрос приходит с **tenant_id** (из подписи SigV4 / JWT / middleware).
- `metadata.Repository` хранит `buckets`, `objects` с `tenant_id`. Запросы **всегда** фильтруются по `tenant_id`.
- **RBAC** (allow/deny таблица) решает, что можно tenant'у: `s3:GetObject`, `s3:PutObject`, `s3:ListBucket`.
- **Audit log** (append-only) фиксирует **каждое** действие: `tenant_id`, `action`, `resource`, `result`. UPDATE/DELETE запрещены правилами БД.

**Что даёт:**
- **Изоляция A/B**: tenant A не видит объекты tenant B, даже если угадает ключ.
- **Аудит**: каждое действие записано, append-only (нельзя подделать/удалить).
- **RBAC**: пустая политика → `403` на всё. Явное разрешение → доступ.

**Что проверяется тестами:**
- `TestTenantIsolation` (A не видит B).
- `TestRBAC` (allow/deny таблица, пустая политика → 403).
- `TestAuditAppendOnly` (INSERT ok, UPDATE/DELETE игнорируются).
- `TestObjectIsolation` (объект в бакете A не виден из бакета B).
